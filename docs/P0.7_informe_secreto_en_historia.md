## 3. Por qué la auditoría A4 pudo verlos igual (explicación honesta)

Los hallazgos tipo «dumps de la DB en la historia» suelen venir de:
1. **Objetos dangling en el repo LOCAL del auditor** (`git fsck --lost-found`):
   commits huérfanos de force-pushes anteriores que GitHub conserva un tiempo
   y que el clon fresco NO descarga.
2. **Otras refs además de `main`** (PR heads cerrados, tags, `refs/pull/*`):
   `git rev-list --all` en el clon solo cubre las refs que se trajeron.
3. **Clones históricos/forks** hechos antes de que el `.gitignore` existiera.

Los tres viven FUERA de `origin/main`; reescribir la rama no los borra de
GitHub (quedan en caché hasta que GitHub ejecute GC tras una limpieza con
Support). Por eso el trámite completo es dos pasos, y solo el primero es local.

## 4. Comando propuesto (NO ejecutado — requiere permiso explícito)

Solo si los pasos de enumeración de la §1-c confirman residuos:

```bash
# 0. Backup completo ANTES (el filter-repo es destructivo e irreversible)
git clone --mirror git@github.com:ALBRA8/YOUTUBE-AUTOMATION.git backup-mirror
cd backup-mirror

# 1. Enumerar lo que realmente hay que purgar (dry-run del propio filter-repo)
git filter-repo --analyze   # informe en .git/filter-repo/analysis/

# 2. Purga por RUTA (las rutas de secretos, no «todo lo que parezca .db»)
git filter-repo --invert-paths \
    --path backend/data/backups \
    --path backend/.env \
    --path backend/data/token.json \
    --path client_secret.json \
    --force

# 3. Verificación post-purga (debe salir vacío)
git rev-list --all --objects | rg -i "env\.bak|token\.json\.bak|client_secret|\.db$"

# 4. Push forzado + invalidación de los objetos en GitHub
git push --force --all
git push --force --tags
# → Abrir ticket con GitHub Support para ejecutar GC e invalidar cachés/refs
#   colgantes en el lado del servidor (esto NO se puede hacer desde git local).

# 5. TODOS los colaboradores: re-clonar (los clones viejos resucitan los
#    commits purgados con un push accidental).
```
